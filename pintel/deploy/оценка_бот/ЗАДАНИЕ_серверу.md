# Задание: поставить приём оценки с точки в тестового бота

Это задание для чата, у которого есть доступ к серверу Pintel. Всё — только в тестовом
контуре: тестовый бот `PintelOlxBot` и база `pintel_ocenka_test`. Рабочий бот Оценки не
трогаем вовсе.

## Что происходит и зачем

Приложение на точке (Pintel Check, exe) проверяет iPhone по кабелю и должно создавать
сделку в Оценке. **Порт Postgres Оценки закрыт наружу**, своего сервера мы не держим,
поэтому в базу с точки хода нет. Канал остаётся один — Telegram, и сделку создаёт сам
бот: он на сервере, база у него под рукой.

Как это работает:

1. Приложение показывает QR со ссылкой `https://t.me/PintelOlxBot?start=p<КОД>`.
   Сотрудник открывает её своим телефоном, бот узнаёт его по `chat_id` — это и есть
   оценщик сделки. Дальше бот ведёт его по шагам: фото экрана с набранным `*#06#`, фото
   лицевой стороны, фото задней, видео. Хранятся они как `file_id`, то есть бесплатно,
   ровно так же, как медиа обычных сделок Оценки.
2. Точку сделки бот берёт от него же: продавец закреплён за магазином — берём его, а
   администратор выбирает магазин кнопкой, когда собраны ВСЕ медиа. В настройках
   программы точки нет.
3. Приложение отправляет сделку JSON-файлом в рабочую группу Telegram: к файлу читаемая
   карточка (модель, память, IMEI, аккумулятор, детали, цена, клиент) и кнопка.
4. Оценщик нажимает кнопку. **Только нажатие и приносит боту посылку**: свои исходящие
   сообщения бот не видит, а в `callback_query` Telegram отдаёт сообщение целиком, вместе
   с файлом. Заодно это подтверждение — в карточке видно ровно то, что уйдёт в сделку.
5. Бот читает файл, добавляет видео и фото, присланные по тому же коду, создаёт сделку и
   передаёт её дальше: статус «Оценен» — карточкой с кнопками «Выкуп»/«Закрыть» оценщику
   в личку, «Ожидает оценку» — админам. Без этого сделка со статусом 1 не видна нигде.
   Создаётся она так:
   `devices` + `device_imeis`, клиент в `users` (staff_id 3), `status_id` по правилу самой
   Оценки. В ответ — номер сделки.

## Ограничения (не нарушать)

* По умолчанию на сервере только чтение: `SELECT`, логи, `grep`. Ничего не менять без
  явного подтверждения пользователя на каждое действие.
* Писать **только** в `pintel_ocenka_test`. Рабочую базу не трогать.
* Перед любым `UPDATE`/`DELETE`: сначала `SELECT` с числом задетых строк, потом бэкап,
  потом сама операция в транзакции с проверкой количества строк. Бэкап:
  `pg_dump -U postgres -Fc ИМЯ_БАЗЫ > ~/имя_$(date +%F_%H%M).dump`
* В `pintel_ocenka` удаление сделки (`devices`) каскадом сносит IMEI, реквизиты клиента и
  начисленные бонусы. Ничего не удалять.
* `pintel_ocenka` и `pintel` — **разные системы с разными наборами ролей**. Здесь речь
  только про `pintel_ocenka` (бот Оценки).
* Перезапуск `ocenka.service` (рабочий бот) рвёт все начатые диалоги продавцов — FSM живёт
  в памяти. Его перезапускать нельзя: только тестового бота. Если почему-то понадобится
  рабочий — лишь с разрешения и в окно 21:30–23:30 или 01:00–07:00 по Алматы.
* На сервере нет git: **перед правкой любого файла сделать копию** рядом
  (`cp main.py main.py.bak_$(date +%F_%H%M)`).
* Секреты (токен бота, пароли, ключи) не выводить в чат и не коммитить никуда.

## Шаг 0. Сначала осмотреться (только чтение)

Это заодно ответы, которых не хватает на нашей стороне — их нужно вернуть в отчёте:

1. Где лежит тестовый бот и как он называется в systemd:
   `systemctl list-units --type=service | grep -i -e ocenka -e olx -e test`
2. Какую базу он использует: его `.env`/`config.py` → `DATABASE_URL` (саму строку с
   паролем в чат не выводить, достаточно имени базы).
3. Версия aiogram в его venv: `pip show aiogram | head -2`.
4. `handlers` — пакет? Есть ли `handlers/__init__.py`.
5. Порядок роутеров в его `main.py`: где `dp.include_router(router_start)`.
6. `SELECT to_regclass('public.kiosk_media');` — не стоит ли таблица уже.
7. `SELECT id, litera, shop_name FROM shops ORDER BY shop_name;` — по этим id программа на
   точке присылает `shop_id` в посылке (точку в боте больше не выбирают); магазинов должно
   быть столько же, сколько в рабочей базе.
8. `SELECT id, name FROM statuses ORDER BY id;` — нужны статусы 1 и 2.
9. `SELECT id, first_name, staff_id, shop_id FROM users WHERE chat_id IS NOT NULL AND staff_id IN (1,2);`
   — у оценщиков должен быть `chat_id` в этой базе, иначе бот не узнает, кто пришёл.
   Заодно видно `shop_id` продавцов: он уже не обязателен — точку присылает программа, —
   но по нему бот называет точку в первом ответе. Кому не хватает — назвать в отчёте,
   **не проставлять самим**.

## Шаг 1. Таблица обмена

Одна новая таблица, чужие не затрагиваются:

```
psql -U postgres -d pintel_ocenka_test -f kiosk_media.sql
```

Проверить: `\d kiosk_media` — должны быть `code UNIQUE`, `user_id`, `chat_id`, `video`,
`photos`, `checks`, `done`, `device_id`.

**Если таблица уже стояла** (её ставили в прошлый раз), файл всё равно нужно прогнать: в нём
появилась колонка `checks` — ручная диагностика. Файл повторный запуск переживает, всё
существующее он пропускает. Без этой колонки новый обработчик **не создаст ни одной сделки**:
диагностику ему будет некуда записать. Ставить колонку и файлы надо вместе.

## Шаг 2. Файлы обработчика

Положить в `handlers/` тестового бота **оба** файла: `kiosk_media.py` и `kiosk_core.py`.
Без второго первый не поднимется (`from handlers import kiosk_core`, с запасным вариантом
`import kiosk_core`, если `handlers` не пакет).

## Шаг 3. Одна строка в main.py

Скопировать `main.py`, потом добавить импорт и включение роутера **до** `router_start`:

```python
from handlers.kiosk_media import router_kiosk_media
...
dp.include_router(router_kiosk_media)   # ПЕРЕД dp.include_router(router_start)
dp.include_router(router_start)
```

Порядок важен: `router_start` ловит любой `/start` и заберёт нашу ссылку себе. Больше в
боте менять нечего — свои `/start` он обрабатывает как раньше, наш обработчик срабатывает
только на `/start p<КОД>`.

Перезапустить **только тестового** бота и посмотреть логи: при ошибке импорта он падает
сразу, и это видно в журнале юнита.

## Шаг 4. Рабочая группа

1. Добавить `PintelOlxBot` в группу сотрудников. Права администратора не нужны,
   приватность выключать не надо: команды со слэша и нажатия кнопок доходят и так.
2. В группе написать `/kiosk_id` — бот ответит `chat_id` (число с минусом).
3. Это число вернуть пользователю: оно пойдёт в `kiosk.toml` как `ocenka_chat_id`.

В группе будут видны имя и телефон клиента — она должна быть только для сотрудников.

## Шаг 5. Проверка

1. Личный чат с ботом: `/start pTEST1`.
   * «Принимаю медиа для сделки…» — всё встало.
   * Обычное меню или тишина — роутер стоит после `router_start`.
   * «Этот код — для сотрудников Pintel» — обработчик работает, но `chat_id`
     проверяющего нет в `users` этой базы или его `staff_id` = 3.
2. Прислать боту три фото, потом видео — бот после каждого называет следующий шаг и
   принимает только то, что нужно на шаге: видео на шаге фото он не возьмёт и ответит
   «Нужно фото». Кнопок в сообщениях нет. Когда собрано всё: администратору — кнопки
   выбора точки, у продавца точка уже стоит.
3. Дальше бот сам присылает **ручную диагностику**: восемь пунктов кнопками и «Готово ·
   осталось N». Нажать по пунктам (⬜ → ✅ → ❌), проверить, что счётчик на кнопке «Готово»
   уменьшается, а «Готово» при неотмеченных пунктах отвечает всплывающим «Не отмечено: …».
   Экран, касание, камеры, динамик и микрофон бот не спрашивает: их прогоняет сам телефон
   клиента на странице теста из киоска, и результат приезжает в посылке.
4. `SELECT code, user_id, shop_id, video, photos, checks, done, device_id FROM kiosk_media ORDER BY id DESC LIMIT 5;`
   — строка с кодом TEST1, `file_id` видео, проставленной точкой и `checks` вида
   `{"bio": true, "cams": true, …}`.
5. Сквозная проверка — вместе с точкой: приложение присылает карточку в группу, оценщик
   нажимает «Создать сделку в Оценке», бот отвечает номером. Проверить, что сделка
   **открывается** в Оценке по кнопке (для этого и нужно видео: карточку она открывает
   через `InputMediaVideo(device.video_phone)` без проверки на пусто).
6. Отдельно проверить шлюз: стереть отметки (`UPDATE kiosk_media SET checks = NULL WHERE
   code = 'TEST1';` — только в **тестовой** базе) и нажать кнопку снова. Бот обязан отказать
   («Не хватает: ручная диагностика: не отмечено …») и прислать диагностику в личку тому,
   кто сдавал медиа. Сделка при этом создаться не должна.
7. И что отметка ❌ снимает автоцену: отметить один пункт как «не работает», создать сделку
   и посмотреть `SELECT status_id, phone_status, comment_ocenka FROM devices ORDER BY id DESC
   LIMIT 1;` — должно быть `status_id` 2, состояние «Присутствует дефект» (а по пункту
   «Детали Apple» — «Ранее был в ремонте») и строка «Ручная диагностика … НЕ РАБОТАЕТ: …».
8. Отдельно: посылка **без** теста на телефоне (её пришлёт точка со старой программой) должна
   создать сделку, а не упасть в отказ — но со `status_id` 2 и строкой «Теста на телефоне не
   было» в комментарии. Это и есть страховка на порядок установки: сборка уезжает на точки
   сама, а эти файлы ставят руками.

При любой ошибке бот пишет причину в тот же чат — молча он не отказывает. Если в чате
`❌ Сделка … не создалась: …`, прислать этот текст.
